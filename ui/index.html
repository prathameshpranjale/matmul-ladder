How a laptop CPU goes from 0.6 to 83 GFLOPS

One problem (multiply two matrices), five steps. Each step changes one thing, and each is measured. This page shows what happens inside the machine, and what we measured.

Machine: Intel Core i5-1235U, WSL2, gcc 13.3. Labels used on this page: measured a number from our runs, illustration a simplified animation to build intuition, not a measurement, hypothesis an explanation that fits the data but that we could not verify (no hardware counters here).

The problem

Multiply two n x n matrices

Each output number is a row of A times a column of B, added up. That is 2 x n³ arithmetic operations. For n = 1024 that is about 2 billion.

for i in 0..n:  for j in 0..n:  for k in 0..n:
    C[i][j] += A[i][k] * B[k][j]

Speed is measured in GFLOPS: billions of operations per second. Higher is better. The CPU is not the slow part of this loop; how it walks through memory is.

Steps 1 and 2

Memory is stored in rows

A matrix lives in memory row after row. When the CPU reads one number, it actually fetches a whole cache line (16 floats on real hardware; 4 in this illustration) into a small fast cache. Next to it is free, if you use it.

illustration

Naive: walk down a column of B

Reordered: walk along a row of B

Red = the number was not in the cache (a miss: slow trip to main memory). Blue = hit. Green outline = a cache line currently held. Try 4 lines: the column walk misses every time. Try 8 or 16: the second column finds its lines still cached. That is why the naive loop is fine for small matrices and falls apart for large ones.

measured

Naive loop slows down as n grows

The reordered loop stays near 3.5 GFLOPS. Same arithmetic, different order. Final run.

What changed in the code

// step 1: B walks down a column
for i: for j: for k:
  sum += A[i][k] * B[k][j]

// step 2: B and C walk along rows
for i: for k: a = A[i][k]
  for j: C[i][j] += a * B[k][j]

Result: about 5.8x faster at n = 1024. hypothesis The reason is cache use; we have no cache-miss counters to confirm it.

Step 3

Work on small tiles that stay in cache

Instead of streaming through a whole row of B every time, cut the matrices into tiles and finish all the work on one tile before moving on, so its data is reused while it is still cached.

illustration

Does the tile fit in the cache?

One B tile is BLOCK x BLOCK floats. Cache sizes are approximate: L1 about 48 KB, L2 about 1.25 MB per performance core estimate

Measured: tile size vs speed (n = 1024)

Small tiles (16 to 96) were slower than not tiling at all (plain reorder is about 2.7 in a comparable session); big tiles won. Median of 3 rounds, rotating through sizes. Overall gain from tiling: about 15% at n = 1024, confirmed by alternating runs. hypothesis Short inner loops add overhead.

Step 4

Do 8 floats at once

The CPU has 256-bit vector registers: 8 floats side by side, and one instruction (fused multiply-add) updates all 8.

illustration

Scalar: one float per instruction

SIMD (AVX2): eight floats per instruction

c[j..j+7] = fma(broadcast(a), b[j..j+7], c[j..j+7])   // one instruction, 8 lanes
measured

Step 3 vs step 4 (n = 1024)

4.1 → 27.4
GFLOPS, median of 6 alternating rounds. Ranges: 3.9 to 4.5 vs 25.7 to 28.6, nowhere near each other. About 6.7x.

What it tells us

Most of the earlier slowness was instruction count, not memory. We are still far from the CPU's limit: every vector multiply-add still does two loads and a store. hypothesis Keeping a small block of C in registers (register tiling) is the usual next step. We did not build it.

Step 5

Split the output across threads

Cut C into 128 x 128 output tiles. Each tile belongs to one thread, so no two threads ever write the same number: no locks, no races.

illustration
12

Measured: threads vs speed

measured 12 threads are about 3.0x (n = 1024) and 3.4x (n = 2048) faster than one SIMD thread, far from 12x. At n = 1024, 4 threads were no faster than 2. hypothesis This CPU has 2 fast performance cores (4 hardware threads) and 8 slower efficiency cores, and a core's two threads share its vector units. Tiny matrices were useless for threads: start-up cost dominated (noise up to 3387% at n = 100).

Why you can believe the numbers

How we checked ourselves

Correct before fast

Every version is compared with a double-precision reference first. The output buffer starts filled with NaN, so a version that skips work cannot pass. Nothing is timed until the answer is right.

Break it on purpose

We skipped the last column in a copy: the harness reported WRONG RESULT (error 0.63) and timed nothing. A check that cannot fail proves nothing.

Alternate, do not sequence

Our first tile sweep ran each size once, in order, and said blocking was slower. The machine's speed was drifting. Alternating rounds and comparing ranges gave the opposite, correct answer.

Show the noise

Every result prints how much the runs differed. Where that was huge (tiny matrices with threads), we did not quote the number.

What this does not show

  • No GPU steps. This machine has no NVIDIA GPU (Windows lists only Intel graphics). CUDA steps need another machine or a cloud GPU.
  • No comparison with OpenBLAS or cuBLAS (not installed), so we cannot say how close we are to a tuned library.
  • No hardware counters (perf does not work here). Every "why" on this page marked hypothesis fits the data but is unverified.
  • One machine, one run family. Absolute numbers will differ on yours; the ratios are what to compare.
  • Next step on the CPU: register tiling. Not built.
